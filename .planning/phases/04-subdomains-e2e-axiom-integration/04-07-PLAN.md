## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Live parity test → network | Live run against hackerone.com and tesla.com makes real DNS/HTTP requests; passive-only sources are fine; active brute/permut hits target DNS |
| Fixture files → parity test | Fixture files are developer-controlled; they are the "frozen v1 reference" for CI |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-23 | Information Disclosure | Live parity test output contains real subdomains | accept | Live parity run is developer-initiated, not CI. Outputs are in workspaces/ directory on developer machine. No automatic cloud upload of scan results |
| T-04-24 | Tampering | Fixture files modified to force parity pass | mitigate | Fixtures are committed to git; any modification shows in `git diff`. The CI test enforces 0% tolerance against the committed fixtures — a test that always passes by design is caught in code review |
| T-04-25 | Denial of Service | Live parity run against hackerone.com/tesla.com at aggressive rate | mitigate | Rate limits (PUREDNS_PUBLIC_LIMIT, HTTPX_RATELIMIT, NUCLEI_RATELIMIT) configured in reconftw.cfg; parity test uses standard config values, not max-rate values |
| T-04-SC | Tampering | Test fixture injection via malformed mock backend output | accept | MockBackend is test-only code; fixtures are static files; no injection surface in test context |
</threat_model>
